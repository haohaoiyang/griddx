# 数据与模型接口交接说明

| 项目 | 当前约定 |
| --- | --- |
| 当前时间粒度 | 日级 |
| 数据处理 | 独立 `data-worker` 进程异步读取、校验、清洗并发布 |
| 模型调用 | 独立 `model-api` 进程使用 FastAPI 提供 REST API |
| 模型运行方式 | 只加载已训练模型推理，生产 API 不训练模型 |
| 数据交换 | XML/DT 使用文件目录；原 CSV 部分改为从 DB 读取 |
| 调用方 | 南瑞方业务系统通过 REST API 调用 |

## 引言

本交付由两个相互独立的进程组成：

1. `data-worker` 由华工方负责，异步读取 XML/DT 与 DB 业务表，执行校验、关联、日级聚合、历史特征加工和版本发布。
2. `model-api` 由华工方负责，只读取 Worker 已发布的数据，调用已训练的设备模型、站点模型和经济调度模型，通过 FastAPI 向南瑞方返回 JSON。

```text
XML/DT 文件 + DB 业务表
              |
              v
  data-worker（异步清洗）
              |
              v
   版本化设备/站点日数据
              |
              v
 model-api（FastAPI + 已训练模型）
              |
              v
       南瑞方业务系统
```

API 请求不会在线扫描原始大表，也不会在线重新训练模型。数据处理失败时不更新当前活跃版本，API 仍读取上一个完整版本。

## 1. 数据部分

### 1.1 输入数据清单

| 序号 | 数据名称 | 原格式 | 接入方式 | 当前时间粒度 | 用途 |
| ---: | --- | --- | --- | --- | --- |
| 1 | CIM 模型数据 | XML/RDF | 文件 | 模型快照，按模型更新 | 设备、站点、测点及关系 |
| 2 | 设备运行状态数据 | DT | 文件 | 原文件内含时间；当前按日聚合 | 电流、电压、功率和开关状态 |
| 3 | 主网设备数据 | CSV | DB | 日级/台账变化时 | 设备基础信息和设备匹配 |
| 4 | 缺陷数据 | CSV | DB | 日级累计历史 | 历史缺陷特征 |
| 5 | 检修单主表数据 | CSV | DB | 日级累计历史 | 检修任务信息 |
| 6 | 检修单设备明细数据 | CSV | DB | 日级累计历史 | 检修单与设备关联 |
| 7 | 变电跳闸记录 | CSV | DB | 日级累计历史 | 变电设备跳闸历史 |
| 8 | 输电跳闸记录 | CSV | DB | 日级累计历史 | 输电线路跳闸历史 |

建议 XML 文件名为 `zs_dicp_model-YYYYMMDD.xml`；DT 文件保持现有 `*.DT` 命名。原 CSV 对应的 DB 逻辑表为：

```text
DM_主网设备
DM_缺陷数据
DM_检修单主表_JXSQD
DM_检修单从表_TD_JXSBLB
DM_变电跳闸记录
DM_输电跳闸记录
```

DB 中可以是表或视图，实际 schema 和名称通过 `DB_TABLE_MAP` 映射，不要求数据中心使用上述物理表名。XML 和 DT 仍由文件目录接入，不从 DB 读取。

### 1.2 XML/DT 放置路径

每个批次使用独立的 `batch_id`，放入共享运行目录：

```text
api_service/runtime/inbox/<batch_id>/
├── xml/
│   └── zs_dicp_model-YYYYMMDD.xml
├── dt/
│   ├── *.DT
│   └── *.DT
└── READY.json
```

当前约束：

| 项目 | 约束 |
| --- | --- |
| `batch_id` | 1～64 字符，只允许字母、数字、`.`、`_`、`-` |
| XML | 每批次必须且只能有 1 个非空 `.xml` 文件 |
| DT | 每批次至少 1 个非空 `.DT` 文件 |
| 站点名称 | 当前清洗规则保留具有中文站名的正式站点，过滤测试站和空站名 |
| `business_date` | 必须存在于本批次处理后的设备日和站点日数据中 |

### 1.3 如何触发清洗

#### 自动触发

先上传 XML/DT，确认文件全部写入完成后，最后放入 `READY.json`。不能在大文件尚未写完时提前生成完成标记。

> 示例说明：下列完成标记会让 Worker 以基础运行数据模式处理 `demo-raw-20260201` 批次。JSON 中不写注释，因此可直接运行。

```json
{
  "request_id": "auto-demo-raw-20260201",
  "business_date": "2026-02-05",
  "run_mode": "operation_only"
}
```

Worker 默认每 2 秒扫描一次 `READY.json`，根据 `request_id` 幂等建立任务。

#### API 手动触发

历史补数或人工重跑可调用 `POST /api/data-jobs`。该 API 只创建任务，真正清洗仍由独立 Worker 执行。详细报文见 2.4 节。

### 1.4 处理模式

| `run_mode` | 输入 | 用途 | 输出质量说明 |
| --- | --- | --- | --- |
| `operation_only` | XML + DT | 文件联调、基础运行评估 | 可运行，但缺陷/跳闸/检修特征不完整，设备结果可返回 `data_quality=warning` |
| `full` | XML + DT + 6 类 DB 业务数据 | 生产日级评估和家族预警 | 从 DB 导出等价数据，补充设备历史、家族三元组和家族统计特征 |

### 1.5 异步处理过程

Worker 实际执行顺序如下：

| 顺序 | 任务阶段 | 处理内容 |
| ---: | --- | --- |
| 1 | `validating` | 检查批次目录、XML/DT 数量和空文件 |
| 2 | `extracting_xml` | 从 XML 解析对象和关系 |
| 3 | `merging_dt` | 将 DT 测点值按 XML 关系关联到设备和站点 |
| 4 | `building_device_daily` | 形成设备日运行宽表 |
| 5 | `exporting_database` | `full` 模式下从 DB 读取 6 类业务数据 |
| 6 | `building_device_model_table` | 形成设备模型基础表 |
| 7 | `building_station_daily` | 按站点聚合设备日数据 |
| 8 | `enriching_device_history` | `full` 模式下加工缺陷、跳闸、检修、家族三元组和家族历史 |
| 9 | `publishing` | 校验业务日期，发布新的设备/站点数据版本 |

数据处理与 API 查询不在同一进程。Worker 使用 SQLite 任务表原子领取待处理任务，避免同一任务被同时处理。

### 1.6 处理结果存储与模型读取

```text
api_service/runtime/
├── state/service.db               # 异步任务状态
├── jobs/<job_id>/                 # 当次中间文件、日志和结果
└── published/
    ├── versions/<feature_version>/ # 不可变设备/站点特征文件
    └── active.json                # 当前活跃版本指针
```

Worker 先写入新版本目录，再原子替换 `active.json`。`model-api` 每次读取当前活跃版本，然后使用模型产物内保存的字段顺序和预处理器进行推理。容器部署时 API 和 Worker 共享该持久化目录。

### 1.7 DB 对接

只有原 CSV 部分从 DB 读取。当前代码已使用 `DATABASE_URL` 和 `DB_TABLE_MAP` 保留数据库接入点，Worker 将数据库表/视图转换为现有清洗脚本可读的等价文件，再执行后续流程。

```env
DATABASE_URL=postgresql+psycopg://user:password@db-host:5432/database
DB_TABLE_MAP={"dm_device":"schema.dm_device","defect":"schema.dm_defect","maintenance_main":"schema.dm_maintenance_main","maintenance_device":"schema.dm_maintenance_device","trip_substation":"schema.dm_trip_substation","trip_line":"schema.dm_trip_line"}
```

实际联调前需由华工方与南瑞方确认：

- DB 类型与版本，例如 Oracle、PostgreSQL、MySQL 或 SQL Server。
- 表或视图名、schema、账号权限和对应的 Python 驱动。
- 字符集、时区、空值、历史数据范围和增量字段。
- 读取账号使用只读权限，密码由部署平台注入，不进入代码和 Git。

家族缺陷预警使用主网设备台账生成“厂家 + 型号 + 批次”三元组。批次按以下顺序取得：优先读取 DB 中的`生产批次`、`设备批次`、`批次`或`出厂批次`字段；没有独立批次字段时，将`出厂日期`归一为 `YYYYMM`，并在接口的 `batch_source` 字段中标记为推导值。厂家、型号或批次任一缺失时，该设备不进入家族预警统计。

### 1.8 秒级/分钟级数据说明

当前设备和站点模型均为日级模型。DT 文件包含 `Time`，但当前流程会将同一设备同一天的多条记录合并为一条设备日记录，保留输入顺序中最后遇到的有效值。

当前设备模型和站点模型均按日进行评估。各类输入数据在现有模型中的时间粒度如下：

| 输入数据 | 当前时间粒度 | 秒/分钟级接入说明 |
| --- | --- | --- |
| `zs_dicp_model-YYYYMMDD.xml` | 日级模型快照，模型变化时更新 | 不需要按秒或分钟重复提供；拓扑变化时及时更新 |
| `*.DT` | 当前模型按日聚合使用 | 需要提供秒级或分钟级连续测点数据，是高频评估的核心输入 |
| `DM_主网设备.csv` | 设备台账，无连续时间粒度 | 不需要按秒或分钟生成；设备属性变化时更新 |
| `DM_缺陷数据.csv` | 事件级记录，当前模型按日统计 | 不需要每秒重复；新增或变更缺陷时及时增量提供 |
| `DM_检修单主表_JXSQD.csv` | 检修单级记录，当前模型按日统计 | 不需要每秒重复；检修状态变化时及时提供 |
| `DM_检修单从表_TD_JXSBLB.csv` | 检修设备关联记录，当前模型按日统计 | 不需要每秒重复；设备关联变化时提供 |
| `DM_变电跳闸记录.csv` | 事件级记录，当前模型按日统计 | 不需要每秒快照；事件发生时间应尽量精确到秒 |
| `DM_输电跳闸记录.csv` | 事件级记录，当前模型按日统计 | 不需要每秒快照；事件发生时间应尽量精确到秒 |

说明：表中 DM 文件名用于标识既有 CSV 数据口径，不代表生产环境继续通过 CSV 文件接入；正式部署时按第 1.7 节从 DB 表或视图读取。

如后续建立秒级或分钟级模型，需提高频率的是第 2 类 DT 运行数据，至少保留：

```text
Time
measurement_id（DT 中的 ID）
Value 或 Status
量测质量码（如现网可提供）
```

XML 拓扑和 DM 业务数据不需要强制提高到秒级，它们按各自更新频率维护。秒级/分钟级能力需新增保留原始时间戳的处理分支并重新训练对应模型，不能将当前日级模型直接宣称为秒级预测。

## 2. API 接口部分

### 2.1 通用约定

| 项目 | 约定 |
| --- | --- |
| 协议 | REST API，当前服务使用 HTTP；生产 HTTPS 由网关终止 |
| 默认端口 | `8000` |
| 格式 | `application/json; charset=utf-8` |
| 日期 | `YYYY-MM-DD` |
| 请求追踪 | POST 使用请求体 `request_id`；GET 可使用 `X-Request-ID` 请求头 |
| 训练 | 所有 API 均不触发模型训练 |
| 单次 ID 数量 | POST 中显式 ID 列表最多 100 个；不传则返回该日全部对象，默认同步上限 10000 条 |

所有成功响应使用统一外层：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `code` | string | `0` 表示成功 |
| `message` | string | 处理结果说明 |
| `request_id` | string | 请求追踪标识 |
| `data` | object | 接口业务数据 |

状态等级统一为：

| `state_level` | `state_name` | 含义 |
| ---: | --- | --- |
| 0 | `normal` | 正常 |
| 1 | `watch` | 关注 |
| 2 | `abnormal` | 异常 |
| 3 | `high_risk` | 高风险 |

> 报文说明：本章示例使用随代码交付的演示数据。启动 API 和 Worker 并执行 `python3 -m api_service.demo.prepare_demo_data` 后，下列 `curl` 可在项目根目录直接联调。JSON 内不加非标准注释；每个示例前的“示例说明”用于说明用途。`request_id`、`job_id`、时间、数据版本和模型分数以实际返回为准。

### 2.2 存活检查

```http
GET /health/live
```

- 请求体：无。
- 接口约束：可选请求头 `X-Request-ID`。
- 响应体：HTTP 200；`data.status=up` 表示 API 进程能响应 HTTP，不代表数据已发布。

> 示例说明：检查 API 进程是否存活。

```bash
curl -H "X-Request-ID: demo-live-001" http://127.0.0.1:8000/health/live
```

```json
{
  "code": "0",
  "message": "success",
  "request_id": "demo-live-001",
  "data": {"status": "up", "service": "model-api"}
}
```

### 2.3 就绪检查

```http
GET /health/ready
```

- 请求体：无。
- 接口约束：必须已有一个成功发布的数据版本。
- 响应体：就绪时返回 HTTP 200 和当前特征版本；未就绪时返回 HTTP 503，`code=FEATURE_DATA_NOT_READY`。

| 响应字段 | 含义 |
| --- | --- |
| `status` | `ready` 表示可接收模型请求 |
| `feature_version` | 当前活跃特征版本 |
| `business_date` | 该版本标识的业务日期 |

> 示例说明：业务系统发流量前检查模型数据是否就绪。

```bash
curl http://127.0.0.1:8000/health/ready
```

```json
{

  "request_id": "req-6b8302c231704896",
  "data": {
    "status": "ready",
    "feature_version": "20260207-demo-seed-081008-f053a8",
```

### 2.4 创建数据清洗任务

```http
POST /api/data-jobs
```

#### 请求体

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `request_id` | string | 是 | 1～96 字符，幂等键 |
| `batch_id` | string | 是 | 必须已存在于 `runtime/inbox/` |
| `business_date` | date | 是 | 本批次业务日期 |
| `run_mode` | string | 是 | `operation_only` 或 `full` |
| `force` | boolean | 否 | 默认 `false`；`true` 创建一次新的重试任务 |

#### 响应体

| `data` 字段 | 含义 |
| --- | --- |
| `job_id` | Worker 任务唯一标识 |
| `batch_id` / `business_date` / `run_mode` | 本次任务的输入标识 |
| `status` | `pending`、`running`、`succeeded` 或 `failed` |
| `current_stage` | 当前处理阶段 |
| `created_at` / `started_at` / `finished_at` | 任务时间 |
| `result` | 成功后的数据版本和行数摘要 |
| `error_message` | 失败时的错误信息 |

#### 接口约束

- `batch_id` 目录必须已存在，且 XML/DT 文件已完整写入。
- 成功接收：HTTP 202。
- 相同 `request_id` 且 `force=false` 时返回原任务，不重复创建。
- API 返回 202 不代表清洗已完成，必须继续查询任务状态。

> 示例说明：手动触发已放入目录的 XML/DT 演示批次。

```bash
curl -X POST http://127.0.0.1:8000/api/data-jobs \
  -H "Content-Type: application/json" \

    "business_date": "2026-02-05",
    "run_mode": "operation_only",
    "force": false
```

### 2.6 设备日分级评估

```http
POST /api/device/assessment
```

#### 请求体

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `request_id` | string | 是 | 1～64 字符 |
| `assessment_date` | date | 是 | 已发布数据中的日期 |
| `device_ids` | string[]/null | 否 | 1～100 个不重复设备 ID；不传或 `null` 表示该日全部设备 |

#### 响应体

| 字段 | 含义 |
| --- | --- |
| `assessment_date` | 评估日期 |
| `model_name` / `model_version` | 设备模型名称和模型文件校验版本 |
| `items[].device_id` / `station_id` | 设备和所属站点 |
| `items[].state_level` / `state_name` | 四级分级评估结果 |
| `items[].confidence` | 预测类别的最高概率 |
| `items[].high_risk_probability` | `abnormal` 和 `high_risk` 两类概率之和 |
| `items[].dominant_discriminator` | 当前设备权重最高的判别器 |
| `items[].discriminator_weights` | 运行、历史、检修和设备画像四个判别器权重 |
| `items[].data_quality` | `pass` 或 `warning`，表示当前输入完整度 |

#### 接口约束

- `assessment_date` 必须存在于已发布数据中；`device_ids` 最多 100 个、不得重复，未传时返回该日全部设备。
- 日期或设备不存在时返回 HTTP 404；请求体校验失败时返回 HTTP 422。

> 示例说明：对两台设备执行 2026-02-07 单日分级评估。

```bash
curl -X POST http://127.0.0.1:8000/api/device/assessment \
  -H "Content-Type: application/json" \
  -d '{
    "request_id": "demo-device-001",
    "assessment_date": "2026-02-07",
    "device_ids": ["AFZ.511C", "AFZ.512C"]
  }'
```

### 2.9 家族缺陷预警

```http
GET /api/defect/family-alerts?assessment_date=YYYY-MM-DD&level=G|M|L&limit=N
```

- 请求体：无。
- 接口约束：`assessment_date` 必填且必须存在于已发布的 `full` 模式数据中；`level` 可选，只能为 `G`、`M` 或 `L`；`limit` 可选，默认 20，范围 1～100。

| `items[].batch_source` | 批次来源；含“推导”时表示由出厂日期生成 |
| `items[].device_count` | 该家族设备总数 |

### 2.15 模型和数据版本查询

```http
GET /api/models
```

- 请求体：无。
- 接口约束：无；可选 `X-Request-ID` 请求头。
- 响应体：HTTP 200；返回实际加载的模型、推理设备和当前数据版本，`data` 字段如下。

| `models[].purpose` | 模型用途 |
| `models[].components` | 设备判别器或站点视图定义 |

### 2.16 错误响应

| HTTP | `code` | 含义 |
| ---: | --- | --- |
| 400 | `INVALID_REQUEST` / `INVALID_DATA` | 参数组合或处理数据不合法 |
| 404 | `DATA_NOT_FOUND` | 任务、日期、设备或站点不存在 |
| 422 | `INVALID_REQUEST` | Pydantic 请求体/查询参数校验失败 |
| 503 | `FEATURE_DATA_NOT_READY` | 尚无可用特征版本，或家族接口读取的不是包含三元组字段的 `full` 版本 |

> 示例说明：请求一个当前数据版本中不存在的设备。

```json
{
  "code": "DATA_NOT_FOUND",
  "message": "Unknown device IDs for the requested date range: ['UNKNOWN-DEVICE']",
  "request_id": "req-9bd38bb99f384d23",
```

### 3.2 具体软硬件要求

#### 生产建议基线

| 类别 | 最低配置 | 建议采购/部署配置 |
| --- | --- | --- |
| 架构 | Linux `x86_64` | Ubuntu 22.04 LTS 或 24.04 LTS `x86_64` |
| API CPU | 4 vCPU | 8 vCPU |
| API 内存 | 8 GB | 16 GB |
| Worker CPU | 8 vCPU | 16 vCPU |
| Worker 内存 | 32 GB | 64 GB |
| 持久化存储 | 200 GB SSD | 500 GB NVMe，再根据 XML/DT 日批次保留周期扩容 |
| GPU | 日级推理可不配 GPU | NVIDIA RTX 3090 24 GB 或同级更高显存 GPU，单卡即可 |
| 网络 | API 端口与 DB 网络可达 | 经 API 网关对南瑞方开放 HTTPS，Worker 不对外开放端口 |

上述 CPU、内存和存储是当前 4.19 GB 原始处理包及日级模型的工程基线，最终采购前应在目标数据量下进行一次全链路压测。当前两个表格神经网络规模较小，GPU 不是日级在线推理的强制条件；如服务器已确定为 3090，可使用 GPU 配置。

#### NVIDIA/CUDA 要求

| 项目 | 当前容器基线 |
| --- | --- |
| Python | 3.11 |
| PyTorch | 2.11.0 |
| PyTorch CUDA wheel | `cu128` |
| CUDA 用户态运行库 | 随容器/PyTorch wheel 安装，宿主机不需单独安装 CUDA Toolkit |
| Linux NVIDIA 驱动最低值 | `570.26` |

| GPU 选择 | `NVIDIA_GPU_ID` 选择宿主机物理 GPU；单卡容器内使用 `TORCH_DEVICE=cuda`、`GPU_ID=0` |

NVIDIA 官方 CUDA 12.8 发布说明列出 Linux 驱动的兼容下限与对应工具包驱动版本；部署时按 [CUDA 12.8 Release Notes](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html) 和 [NVIDIA Container Toolkit Installation Guide](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) 复核。

### 3.3 Docker 启动

在项目根目录复制环境文件：

```bash
cp api_service/.env.example api_service/.env
```

CPU 环境首次构建并准备演示数据：

```bash
docker compose -f api_service/compose.yaml build model-api

  model-api python -m api_service.demo.prepare_demo_data

```

3090 GPU 启动：

```bash
docker compose \
  -f api_service/compose.yaml \
  -f api_service/compose.gpu.yaml \
  up --build -d
```

验证：

```bash
docker compose -f api_service/compose.yaml ps
curl http://127.0.0.1:8000/health/live
curl http://127.0.0.1:8000/health/ready
docker compose -f api_service/compose.yaml exec -T \
  model-api python api_service/demo/run_smoke_test.py
```

Swagger 地址为 `http://127.0.0.1:8000/docs`。日志与停止命令：

```bash
docker compose -f api_service/compose.yaml logs -f --tail=100
```

### 3.5 部署时必须确认的信息

| 类别 | 待华工方与南瑞方确认的内容 |
| --- | --- |
| 服务器 | Linux 发行版、`x86_64`/`aarch64`、CPU、内存、磁盘 |
| GPU | 型号、数量、显存、允许使用的 GPU 编号和 `nvidia-smi` 输出 |
| 容器 | Docker/Containerd 版本、Compose 版本、NVIDIA Container Toolkit |
| DB | 类型、版本、schema、表/视图名、驱动、字符集、时区、只读权限 |
| 文件区 | XML/DT 上传协议、共享路径、用户/UID 权限、保留周期 |

| 业务规模 | 每日 XML/DT 大小、设备/站点数、保留周期、API 并发与 SLA |

DB 未确定前，可使用 `operation_only` 完成 XML/DT 全链路联调；生产 `full` 模式必须在 DB 类型、驱动和 6 类逻辑表映射确认后进行验收。
